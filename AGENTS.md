# Architecture rules
- Appraisals reuse staff_appraisals and scores; atomic server save and locked workflow transitions enforce command scope, non-self approval and immutable events, with workflow_state authoritative and legacy status retained — why: prevent partial scores, bypassed decisions and duplicate registers.
- Staff Mapping edits use a caller-scoped context and optimistic assignment check, then reuse command_move_officers for lifecycle/audit and shared dashboard invalidation; mapping reads exclude deleted personnel — why: unit selection cannot bypass command authority or silently overwrite newer postings.
- Pending HR reuses StaffApplications stage filters and the command-head approval queue; external postings require an explicitly linked active profile, and posting updates assignment/service history atomically through existing RPCs — why: a posted label must represent actual personnel changes, not a duplicate register or inferred identity.
- Duty dashboard totals use caller-RLS aggregates of existing assignments, approved leave and excuse forms, count distinct non-deleted officers and never return medical details; personal summaries are server self-scoped — why: expose real availability without duplicate registers or automatic leave/attendance changes.
- Human Resource links reuse existing permission-gated staff screens and the hub uses the shared exact HR aggregate; application lists fetch every authorized page — why: one real-data workflow without duplicate screens, deleted-inclusive totals or silent record caps.
- Record lists use the shared fixed-25 usePagedList pager; shared tables expose inline horizontal fast navigation and the shell targets active nested scrollers with a document fallback — why: consistent navigation without slicing aggregates, exports or authorization scope.
- Bio-Data export audit stores canonical file extensions (docx/xlsx for Word/Excel); the menu awaits authorized logging and invalidates HR totals after successful generation — why: UI format names must not violate audit constraints or silently lose real download events.
- Dashboard session synchronization uses one debounced, authenticated subscription to published non-audit tables plus existing query polling; HR overview totals use an invoker aggregate RPC and exclude deleted personnel — why: prevent duplicate sockets, capped counts, leaked preview PII and false freshness signals without adding write queues.
- Shift Roster reuses the personal shift tracker and server-attributed roster clock action; Attendance Overview reads the same attendance records with realtime invalidation and polling — why: avoid duplicate registers and client-invented attendance times.
- Holding Center identity verification uses private photos, server-matched staff IDs and Super Admin-only review; approved access is read-only and scoped to the current assigned Command, without changing signing or operational authority — why: verifying identity must not grant administrative powers.
- Command Operations reuses legacy workflow pages in permission-gated tabs; legacy routes preserve record context, Holding Center resolves record links through caller-scoped reads, and edit links reuse existing admin/OIC authority — why: consolidate navigation without losing the selected case or expanding access.
- Command Operations Dashboard reads exact detainee counts, pending bail authorization and unfinished repatriation chains, and daily attendance validation through caller-scoped reads; each section requires its existing module permission and refreshes on record changes — why: consistent totals without broadening access or duplicating registers.
- Bail/repatriation signing-role configuration is saved atomically through `save_approval_chain`, restricted to Super Admins; `sign_approval` reads configured roles on each sign — why: labels must never substitute for actual signing authority.
- Approval signing verifies the current account using an isolated nonpersistent auth client; `sign_approval` requires fresh password AMR and derives the staff name, timestamp and signature server-side — why: prevent typed-name impersonation without switching the app session.

- Date entry uses shared DateInput/DateTimeInput controls with DD/MM/YYYY display and ISO machine values — why: prevent browser-locale regressions across staff and operational forms.
- Keep personnel bio-data editing in the responsive web form; load related record sections separately and block saves after incomplete loads, so a failed fetch cannot overwrite existing details.
- Check record-email recipients on the server against staff addresses or administrator-approved external contacts on every send, including CC, BCC, bulk and saved lists; client pickers are convenience only.- Staff Officers (without admin/OIC/2IC) are command-scoped by restrictive RLS policies (`so_can_see_*`) and reach restricted modules only via per-person `command_tier_grants` set by a Super Admin — why: prevent cross-command HR access at the API layer.
- Audit trails are purged only via `purge_audit_records` (admin or granted admin, ≥30 days old, reason, self-logged); immutability triggers allow deletes only inside it — why: controlled retention without weakening tamper protection.
- Command Vault files are owned by an org unit, stored beneath that unit's path prefix, and accessed only through command-scoped RBAC with immutable action logging — why: prevent cross-command document disclosure and preserve evidentiary history.

- Staff deletion/transfer side-effects run in the `profile_lifecycle_sync` trigger on profiles (deleted_at / org_unit_id); retained history goes to admin-only `staff_record_archive` — why: every delete/transfer path cleans up consistently.

- M&E Communications workspace lives in `me_*message*` tables; all sends go through the `me_send_message` security-definer function — why: one server-side place enforces sender role, command scope and audit.

- Staff import AI comparisons are advisory: authenticate import administrators on the server, read candidates through caller-scoped RLS, minimize prompt fields, validate returned candidate references and audit runs; never let AI modify import outcomes or staff records — why: probabilistic matches cannot authorize personnel changes.
- Staff list import approvals retire only the server-computed set confirmed through `confirm_staff_list_retirements` (same admin, exact count, 30-minute window); `commit_staff_list_import` refuses otherwise — why: a stale or changed list must never silently inactivate staff.
- Regional Commands (`/regional-commands`) is the post-login landing screen; card visibility, counts and activation come from security-definer RPCs (`regional_commands_overview`, `set_command_activation`, `save_command_order`), and display order is separate from reporting relationships; card destinations use current analytics RBAC or the own-card personal portal fallback, and hierarchy dashboard links require analytics permission — why: visual layout must never change assignments, leak other regions or direct ordinary officers to denied analytics. HierarchyView reorders same-parent siblings only; Word exports are audited HTML blobs.
- System colours come from the active row in `app_brands`; BrandingProvider emits mode-scoped CSS tokens with measured contrast, while next-themes owns persistent root Light/Dark/System state; built-in brands are never edited or deleted and interactive brand changes use admin RPCs — why: inline light tokens must not override dark mode or reset workflows.
- Shared Card and its slots use data-ui markers for centralized surface, border, radius and shadow rules; department tabs and charts use semantic theme tokens, not department-specific color overrides. HorizontalStrip contains dashboard overflow and the shared shell Home targets the post-login route — why: consistent readable styling and navigation without changing calculations or permissions.
- Single staff account creation lives at /hr/create-account (CreateStaffAccount) and provisions through the bulk-create-accounts edge function with an optional admin-chosen password (targeted single profile only) — why: one server-side path enforces admin authority, command scope, role allow-list and password policy.
- HRM service records (staff_appointments/promotions/exits) and staff_transfer_requests use hrm_can_record/hrm_can_view RLS; promotion/exit/transfer decisions run only through security-definer RPCs, and approved transfers call command_move_officers — why: rank/status/posting changes stay server-authorised and reuse lifecycle sync.
- KYC visibility (sensitive fields, photos, documents) is decided per profile by the `kyc_access` RPC; exports and the profile KYC tab follow it — why: rank-based masking must be server-decided, not a client role guess.
- Staff Applications submits self/scoped selected-profile requests through record_staff_application; locked review RPCs enforce stages and prevent self-approval with immutable history; transfers keep their own approval steps and posting reuses command_move_officers/staff_appointments — why: one server-authorised pipeline without duplicate requests or racing decisions.
- Transfers and promotions are approved by command OIC/2IC via `is_command_head_for` (role + `user_org_scope`) in `recommend_staff_transfer`/`decide_staff_transfer`/`decide_staff_promotion`, with Super Admin override; queue via `command_approval_queue` — why: approval authority follows the command, not general HR roles.
- Org selectors fold HQ wrappers via buildOrgTree (editors: collapseHq:false) — why: one HQ entry, parents unchanged.
- Pending HR command reassignments are proposals; officers move only when the releasing command OIC/2IC or Super Admin approves via decide_command_reassignment (no self-decision, stale-assignment check, immutable events) — why: postings are reviewed before mapping changes.

- Staff Tier/custom roles: save_staff_tier_definition, assign_staff_tier, save/assign_custom_role.
- Staff Vault: owner writes; reads via `staff_vault_can_view` — why: no role-only access.
- `admin` = global Super Admin: `user_org_scope` returns all units for it — why: authority must not depend on posting.
